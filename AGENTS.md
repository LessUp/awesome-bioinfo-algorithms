# AGENTS.md

## OpenSpec-Driven Development

This project follows **OpenSpec** for specification-driven development (SDD). The `openspec/specs/` directory is the single source of truth for all requirements.

### Workflow

1. **Propose a change**: Use `/opsx:propose <idea>` to create a change proposal
2. **Review specs**: Read relevant specs in `openspec/specs/` before implementing
3. **Implement tasks**: Use `/opsx:apply` to implement tasks from the proposal
4. **Archive when done**: Use `/opsx:archive` to finalize and update specs

### OpenSpec Commands

| Command | Description |
|---------|-------------|
| `/opsx:propose <idea>` | Create new change proposal with specs, design, and tasks |
| `/opsx:apply` | Implement tasks defined in the current change proposal |
| `/opsx:archive` | Archive completed change and update living specifications |

### Spec Capabilities

| Capability | Location | Purpose |
|------------|----------|---------|
| product-vision | `openspec/specs/product-vision/spec.md` | WHAT to build - product requirements |
| core-architecture | `openspec/specs/core-architecture/spec.md` | HOW to build - technical design |
| cli-interface | `openspec/specs/cli-interface/spec.md` | CLI command contracts |
| algorithm-schema | `openspec/specs/algorithm-schema/spec.md` | YAML data schema |
| testing-strategy | `openspec/specs/testing-strategy/spec.md` | Test requirements |

### When to Propose vs. Directly Edit

| Situation | Action |
|-----------|--------|
| Fixing a typo, updating a URL, adding one algorithm entry | Edit directly, no proposal needed |
| Adding a new CLI command, changing validation rules | `/opsx:propose` → `/opsx:apply` → `/opsx:archive` |
| Any change touching multiple specs or Python modules | `/opsx:propose` → `/opsx:apply` → `/opsx:archive` |
| Updating a living spec to match already-merged code | Direct edit to the spec, no proposal needed |

### Branch Strategy

Keep branching lightweight:

- **Trivial fixes** (data entries, docs, single-file edits): commit directly to the default branch (currently `master`).
- **Non-trivial changes** (new feature, refactor, multi-file): create a short-lived branch named `<type>/<short-description>` (e.g. `feat/add-blast-entry`), merge via PR, delete branch after merge.
- Avoid long-lived branches. Changes should be small enough to merge within a day or two.
- After merging, regenerate outputs if `data/` or templates changed (see **Generated Outputs** below).

### When to Use `/review`

Invoke `/review` (the `requesting-code-review` skill) before merging when:

- The change touches Python logic in `awesome_bioinfo/`.
- The change modifies a living spec in `openspec/specs/`.
- The change adds or removes a category.
- You are unsure whether the implementation matches the spec.

Skip `/review` for pure data additions (new algorithm YAML entries that pass `validate`) and documentation-only typo fixes.

### MCP vs CLI Skills

- Use MCP for **external GitHub state**: repository metadata, issues/PRs, Actions runs/logs, and other remote settings.
- Use local CLI skills for **repo-contained maintenance loops** where the source of truth is already in the checkout.
- Current high-value local skills:
  - `verify` — quick lint + typecheck sanity check
  - `updating-algorithm-data` — category / algorithm YAML changes, validation, regeneration, and generated-output drift checks

## Project Commands

```bash
# Validation
python -m awesome_bioinfo validate          # Validate all YAML data
python -m awesome_bioinfo stats             # Show statistics

# Search & Info
python -m awesome_bioinfo search <query>    # Search algorithms
python -m awesome_bioinfo info <id>         # Show algorithm details
python -m awesome_bioinfo compare <id1> <id2>  # Compare algorithms

# Export
python -m awesome_bioinfo export --format json  # Export data

# Generation (run after data changes)
python -m awesome_bioinfo generate          # Generate README.md
python -m awesome_bioinfo mkdocs            # Generate mkdocs/docs/

# Testing
python -m pytest tests/ -v --tb=short
python -m pytest tests/ -k "keyword" -v     # Focused test

# Lint/Typecheck
ruff format awesome_bioinfo/ tests/
ruff check --fix awesome_bioinfo/ tests/
mypy awesome_bioinfo/ --ignore-missing-imports
pre-commit run --all-files                  # All-in-one
```

## Generated Outputs (Do Not Hand-Edit)

- `README.md` — generated by `python -m awesome_bioinfo generate`
- `mkdocs/docs/` — generated by `python -m awesome_bioinfo mkdocs`

> **Note:** `README.zh-CN.md` is a manually maintained Chinese portal document. It is NOT
> auto-generated; do not attempt to regenerate it with `--lang zh`.

After changing `data/` or templates, regenerate and verify:
```bash
python -m awesome_bioinfo generate && python -m awesome_bioinfo mkdocs
git diff --exit-code -- README.md mkdocs/docs/
```

## Algorithm Entry Validation

**Required fields:** `id`, `name`, `description`, `purpose`, `time_complexity`, `category`

**Critical rules:**
- `description`: 50-500 characters (trimmed)
- `id`: lowercase, hyphenated, globally unique (e.g., `smith-waterman`)
- `tags`: lowercase, hyphenated (e.g., `dynamic-programming`)
- `category`: must exist in `data/categories.yaml`
- `subcategory`: must belong to the specified `category`
- `difficulty`: `beginner` | `intermediate` | `advanced`
- `time_complexity` / `space_complexity`: must match `O(...)` pattern

Template: `templates/algorithm_template.yaml`
Schema: `schemas/algorithm-schema.json`
Spec: `openspec/specs/algorithm-schema/spec.md`

## Change-Based Verification

| Change | Commands |
|--------|----------|
| Python code | `ruff`, `mypy`, relevant pytest |
| `data/algorithms/*.yaml` | `python -m awesome_bioinfo validate` |
| Templates | regenerate outputs, verify diff |
| CLI behavior | run the specific CLI command |

## Architecture

- `openspec/` — OpenSpec specifications and change proposals
- `awesome_bioinfo/` — main package, CLI via `__main__.py`
- `data/algorithms/` — 16 YAML files, one per category
- `tests/` — pytest + Hypothesis property-based tests
- `scripts/` — **deprecated**, use `python -m awesome_bioinfo`
